Checks every configured OpenID and SAML provider against the same rules a save is refused by, and lists the ones a login would fail on. It changes nothing and never blocks a save. Whether an identity provider answers is not part of this check: use Test Connection in a provider's own editor for that.

    Adding a provider

    Five steps from an empty form to a provider whose endpoint has answered. A step opens the next only once it is complete, and names what is missing when it is not. Back is always available, and leaving the wizard leaves the editor exactly as it stands.

    1. Protocol and template
    2. The required fields
    3. The address to register
    4. Test the connection
    5. Enable the provider

    Pick the protocol your identity provider speaks. The editor below opens on the one you choose, and its Start from a template picker fills the endpoint shape and the scopes for a provider it knows. A template is optional: leave it unchosen for a provider it does not.

    Fill every field marked required in the editor below, then press Save. Nothing else on the form is needed yet, and no accordion has to be opened for it: the required fields are in Connection, which is open already.

    Copy the address in the editor below with the button beside it, and register it at your identity provider as the redirect or assertion-consumer URL. The value is the one this server computes, which is why the field is read-only.

    Press Test Connection in the editor below. It asks the identity provider itself, and this step opens the next only once that test has succeeded, so the provider you go on to enable is never one whose endpoint has not answered.

    Tick Enabled in the editor below and press Save. Until you do, the provider exists and is offered to nobody on the sign-in page, which is where every provider this wizard builds starts.

    Full text
    Refuse login unless the provider's discovery document advertises PKCE (S256) in code_challenge_methods_supported (RFC 9700 §2.1.1). When off, an unsupported provider only logs an audit warning and the login proceeds.

    Account adoption (sensitive)
    Full text
    ⚠ Sensitive: lets a first SSO login adopt (take over) a pre-existing, unlinked Jellyfin account whose username matches the SSO name, instead of rejecting it. Off by default (fail closed). Enable only for the one-time legacy-link migration window described in the account-linking runbook on the wiki, then turn it back off.     Full text
    Creates an unknown identity's account disabled, with no permissions on its first login and refuses that login until an administrator approves it. Approve the account on the Accounts tab, in the Waiting for Approval panel, or enable it under Administration → Users. Off by default, so new accounts start enabled. An existing or adopted account is never disabled by this, and each deferral is recorded as an audit event.
    Full text
    When someone is renamed at the identity provider, their Jellyfin account is renamed to match on their next SSO login. Off by default; the Jellyfin name then stays as it was and the two drift apart. This changes the display name only: the account is found by its stable subject identifier either way. Turning this on therefore cannot change which account a login reaches. The new name is cleaned up the same way a newly created one is. If another account already holds the name, the rename is skipped and both keep their names. A rename that fails for any other reason is logged and the login still succeeds. Each rename is recorded as an audit event.
    Full text
    ⚠ Sensitive: only meaningful with Allow Adopting Existing Accounts above. The login must then carry a provider-verified email, with email_verified exactly true, before a same-named account is adopted. That narrows who can exploit the name-based match. Needs the email scope, or the provider never returns the claim and every adoption is refused. Off by default, so an existing deployment relying on adoption is not silently locked out. An administrator account is never adopted regardless of this setting.
    Full text
    ⚠ Sensitive: every OpenID login through this provider must carry a provider-verified email, with email_verified exactly true. A login whose email_verified is absent, false or unreadable is refused, whether it adopts, creates or signs in to a linked account. Needs the email scope, or the provider never returns the claim and every login is refused. Off by default, so a deployment that does not set it is unaffected. Independent of the two adoption settings above: run either, both or neither.
    Insecure options
    Full text
    These options disable OpenID Connect security defenses. Enable one only if your provider genuinely requires it; each is recorded as an audit warning.
    Full text
    ⚠ Insecure: drops TLS on the discovery, JWKS and token endpoints. A man-in-the-middle can then swap the id_token signing keys and a forged login is accepted. Use only on a trusted internal network. Enabling it is recorded as an audit warning.
    Full text
    ⚠ Insecure: disables endpoint-origin validation (a mix-up defense). May be required for Google OpenID, whose endpoints live on different hosts. Enabling it is recorded as an audit warning.
    Full text
    ⚠ Insecure: relaxes the outbound SSRF and DNS-rebind guard for this provider, so an OIDC provider on a private network can be reached. It covers this provider's discovery, token and userinfo requests, and an avatar served from the origin of those endpoints up to the first redirect. Every other avatar and SAML metadata are fetched without it. Permits RFC 1918, CGNAT and IPv6 unique-local addresses; loopback, link-local and cloud-metadata ranges stay blocked. Leave off for any provider reachable on the public internet. Enabling it is recorded as an audit warning.
    Full text
    ⚠ Insecure: disables matching the discovery issuer, a mix-up defense. Only for a provider that legitimately presents a different issuer (some templated/multi-tenant setups). Enabling it is recorded as an audit warning.
    Full text
    ⚠ Insecure: disables the RFC 9207 iss check, an OpenID Connect mix-up defense. Only for a provider whose authorization response legitimately carries a different issuer. Enabling it is recorded as an audit warning.
    Full text
    Validates the saved provider over the same hardened, HTTPS-checked path the login uses. The server fetches the discovery document and reports the issuer, the endpoints and whether the JWKS is reachable. Save the provider first. Requires administrator privileges; the client secret is never shown.
